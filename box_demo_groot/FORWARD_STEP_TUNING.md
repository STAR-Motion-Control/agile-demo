# GR00T-WBC 前进小步"腰晃脚不走/反而后退" — 根因 + 方案

box_demo 让底座前进一小段(如 4cm),现象:**腰晃、脚只踏一下、甚至净后退**。
本文是 5080 MuJoCo 实测(`scene_29dof` + 真 Balance/Walk onnx,和真机同一套 policy 权重)
找出的根因、极限、和一组**可调接口 + 推荐值**,供真机测试。

> 实验脚本:`scratchpad/groot5080/sweep_step_limit.py`(headless、CPU onnx、无 DDS,复现
> `run_mujoco_gear_wbc.py` 的 obs/PD/policy)。代码改动:`groot_mover.py` / `remote_mover.py`。

---

## 1. 根因(实测)

**(a) 启动加速斜坡**:从站立起步,Walk 步态要 **~0.6–0.8s** 才达到巡航位移速率。所以
一次前进命令的"净位移 / 命令位移"效率:T≤1.0s 只有 **35–45%**,T≥2s 升到 **55–70%**
(固定的斜坡代价被摊薄)。**短命令 = 大部分时间在爬斜坡,净位移很小。**

**(b) 符号不稳定(就是"反而后退"的元凶)**:T≤0.8s 时,净位移**取决于命令下发瞬间机器人
残余站立摆动的相位** —— 同一条 `0.08m/s × 0.6s` 命令,净位移能从 **−7.4cm 到 +2.2cm** 乱跳:

```
vx=0.10 T=0.6  按下发相位的净位移: -3.2  -7.4  -3.7  +2.2  +1.9  +0.5   (min -7.4, max +2.2)
vx=0.12 T=0.8  按下发相位的净位移: -3.1  -6.8  -3.1  +2.8  +2.5  +1.1
```

短前进命令**在符号上就不可靠**,不只是"小"。机器人**从不摔**(全程 0 摔),只是没有净前进。

**关键**:符号不稳只发生在**没站稳(残余摆动)时起步**。跨摆动相位测更长命令:

```
                    起步相位(越靠左越没站稳) ->        越靠右越站稳
vx=0.12 T=1.2 净位移: +2.9 -2.3 +0.7 | +7.5 +7.2 +5.8   最差 -2.3(仍会后退!)
vx=0.15 T=1.2 净位移: +4.4 -1.0 +3.4 | +9.7 +9.4 +8.0   最差 -1.0
vx=0.15 T=1.5 净位移: +6.6 +0.4 +6.4 | +13.1+12.3+10.9  最差 +0.4(vx>=0.15/T>=1.5 才不再后退)
vx=0.20 T=1.2 净位移: +7.2 +1.3 +7.8 | +14.1+13.5+12.4  最差 +1.3
vx=0.12 T=2.0 净位移: +9.7 +3.4 +6.6 | +12.8+12.4+10.9  最差 +3.4
```

→ 两个结论:**① 站稳后起步永远强净前进(+7~+13cm);后退尾巴只在没站稳时出现。② T≤1.2s 即使
vx=0.15 最差相位仍会 −1cm,要 T≥1.5s(vx≥0.15)或 T≥2.0s(vx=0.12)才跨相位不后退。**
所以主治手段是**移动前先站稳(settle)**,配合 T≥1.5s。

**净位移标定表(站稳后起步,cm)** —— 横轴 T(s),纵轴 vx(m/s):

```
        T=0.6  0.8  1.0  1.2  1.5  2.0  2.5  3.0
vx=0.08  1.6  1.6  3.1  4.3  5.7  7.4 10.2 12.7
vx=0.10  2.2  2.2  4.2  5.8  7.7 10.1 13.7 17.1
vx=0.12  2.8  3.1  5.5  7.5 10.0 12.8 17.7 21.7
vx=0.15  3.6  4.3  7.2  9.7 13.1 17.2 23.2 28.5
vx=0.20  5.4  7.5 10.6 14.1 18.3 24.7 32.5 40.4
vx=0.25  7.2 10.7 13.6 18.4 24.0 31.7 42.0 51.2
vx=0.30  9.7 14.4 17.1 23.3 30.2 39.6 52.3 63.4
```

**极限**:**站稳后**,可靠净前进的最小增量 ≈ **8–10cm**(vx=0.12~0.15 × T=1.5s);跨摆动相位不后退需
**T≥1.5s(vx≥0.15)**。速度太低也不行:floor 若只 0.08m/s,即使 T=1.5s 也只净 ~5.7cm(<8cm),所以
floor 提到 **0.12m/s**(×1.5s ≈ 10cm,真正走出最小增量)。

## 2. 另外两个实测结论

**(c) 下蹲不能走路(回答 SAM3D 蹲高)**:Walk policy 在 **~0.70m 以下就不迈步了**。

```
vx=0.15 T=1.5:  h0.74→+13.1cm(5步)  h0.72→+10.6  h0.70→+10.7(5步)  h0.68→+3.2(3步)  h0.66→0(0步)  h0.64→0(0步)
```

→ **不能边蹲边走。** h0.70 还能走但已是最后一档,h0.68 就崩(只 3cm)。抱箱行走要在**≥0.72m**
(留一档余量)下走;要蹲(捡地上的箱/低桌放箱)
只能**站定后原地蹲**。所以 SAM3D 若返回"箱子在地上",流程应是:**站立高度走到位 → 停 → 原地下蹲
→ 抓/放 → 站起 → 再走**,而不是发一个"边走边蹲"的指令。

**(d) 转向(yaw)本来就好**:效率 65–89%,连 T=0.6s 都可靠。转角不是问题,不用改。

## 3. 方案:一组可调接口(已实现在 `groot_mover.py`,`RemoteMover` 同样生效)

都是 `GrootMover(...)` 的构造参数 / 属性,box_demo 里可直接传或改。已给出**数据支撑的默认值**;
标 *opt-in* 的默认关,测试时打开对比。

> **⚠️ sim2sim 修正(2026-07-01)**:把**真的 `groot_mover.py`**(不是复现脚本)接进 policy sim 端到端测
> (`sim2sim_groot_mover.py`),推翻了"settle 是主手段"的结论 —— **固定 settle 反而会停在坏相位**
> (摆动是周期的),`settle=0.5` 在每个 warmup 配置里都比 `settle=0` 差。**真正治后退的是 warm-up**:
> `warmup=0.6s@0.15` 让跨所有摆动相位的最差净位移 **严格 >0(+3.9cm,绝不后退)**,不加 warmup 最差 −4.9cm。
> 站稳(≥2.5s,管线感知停顿即是)后即使不 warmup 也可靠(最差 +8cm)。→ **默认改成 warmup 开、settle 关。**

| 接口 | 默认 | 作用 | 推荐/说明 |
|------|------|------|-----------|
| **C `warmup_time`** | **0.6** | 移动前按 `warmup_speed`(0.15) 冲这么久预热步态 | **治后退的主手段**:确定性把步态起来, 最差相位也净前进(+3.9cm)。代价:每步变成~10cm+(warmup 本身走 ~0.15×0.6)。0=关。 |
| **A `min_duration`** | **1.5** | 一次移动最短执行时间(s) | T≤1.2s 最差相位仍后退;T≥1.5s(vx≥0.15)才跨相位可靠。**大移动不受影响**(自然时长>1.5s 时按原时长)。 |
| **B `min_distance`** | **0.08** | 把 <此值 的线性目标顶到此最小增量(m) | 小于 ~8cm 不可靠;顶到 8cm,剩余靠 perceive→move→re-perceive 收敛。设 0 关闭。 |
| `v_floor` | **0.12** | 小移动的最低速度(m/s) | 0.08 太慢(×1.5s 只 5.7cm<8cm);0.12 ×1.5s≈10cm,floored 小步才真正走出最小增量。 |
| `settle_before_s` | **0**(默认关) | 移动前先原地 Balance 这么久(s) | **反直觉**:摆动周期性 → 固定 settle 可能停在坏相位,sim2sim 里 settle=0.5 每次都比 0 差。用 warmup 代替。 |
| **E `walk_min_height`** | **0.72** | 低于此高度走路会告警(可选自动抬高) | 见结论(c)。0.70 就在崩塌悬崖边(0.68 只 3cm),0.72 留一档余量。`auto_raise_for_walk=True` 则移动前自动抬到 0.72(会等抬升 slew 完成)。 |
| **D `dist_gain`** | 1.0(*opt-in*) | 开环补偿:实际≈命令×55–60%,设 ~1.7 让单次开环更准 | 闭环(重感知)本就能纠;想少迭代几次再开。开了要配合更长命令否则补偿后目标在默认时长下走不完。 |

**默认即"可靠组合"(sim2sim 验证过绝不后退)**:`warmup_time=0.6` + `min_duration=1.5` + `min_distance=0.08` + `v_floor=0.12` + `walk_min_height=0.72` + `settle_before_s=0`。
一条 4cm 请求 → 顶到 8cm → floored → **先 0.15×0.6s 预热 → vx=0.12×1.5s**(跨相位净 +4~+18cm、绝不后退)。
不想每步这么大(warmup 让步变~10cm+)、且能保证机器人站稳≥2.5s 再走 → 可 `--warmup-time 0`(站稳后仍最差 +8cm)。要更准的开环再加 `dist_gain≈1.7`。

**为什么这样治**:A 把每次移动推进"可靠区";B 保证一步有意义的增量;C/settle 直接压斜坡+摆动
两个失败模式;E 防"蹲着走不动";D 补开环欠速。**闭环的重感知仍是最终纠偏者**,A/B/C 只保证"每步真往前、绝不后退"。

## 4. 怎么在真机测(box_demo)

代码里的 mover 构造已支持这些参数(见 `box_demo_main.py` 的 `--fwd-*` 系列 CLI,若已接;
否则直接改构造)。逐项对比测:

1. **基线(只开 A+B,默认)**:跑一次前进小步,看是否不再后退、每步 ~4–8cm 稳定前进。
2. **加 C 预热**:构造 `warmup_time=0.4`,看短步净位移是否更大更稳。
3. **加 settle**:`settle_before_s=0.5`,看连续两步之间是否更稳(不后退)。
4. **开 D 标定**:`dist_gain=1.7`,看单次开环是否更接近目标(会略过冲,闭环收)。
5. **蹲高**:先 `set_height(0.72)` 走到位 → `stop()` → `set_height(0.50)` 蹲 → 抓/放 → `set_height(0.72)` 站起。
   **别在 <0.70 时发走路命令**(会告警且不迈步)。

> 判据:每次前进命令后 base **净向前**、幅度随 T/vx 单调、**绝不净后退**;蹲下时不试图走路。

## 5. 真机转移注意(实测是乐观下界)

MuJoCo 是理想的(命令瞬时生效、无通信延迟、理想摩擦)。真机上:
- 真 adapter 的 wbc_policy 可能对 `navigate_cmd` 做**插值/缓变** → 起步比 sim 更慢 → 真机需要**更大**的 min_duration/min_distance 余量。
- HTTP→IPC→adapter 有延迟、`cmd_stale_s=0.4` 窗口。RemoteMover 用单条 `/cmd?duration` 让**服务端**保持时长,已避免逐拍网络抖动。
- 地面摩擦/脚底柔顺 → 每步实际前进可能更少。

→ 以上默认值当**起点**,真机上若仍偏保守/偏冲,按第 3 节旋钮微调;数值以真机为准。
